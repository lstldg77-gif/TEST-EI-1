## 1. Python 기초

### 1-1. 변수란 무엇이고, 왜 사용하나요?

**한 줄 요약:** 값에 이름을 붙여 저장해 두는 상자입니다.

**🎤 말하기**

> 변수는 값을 저장해 두는 이름표 붙은 상자입니다. 프로그램은 실행 중에 값을 기억해야 할 때가 많은데, 변수가 없으면 그 값을 다시 쓸 방법이 없습니다.
> 예를 들어 퀴즈를 풀 때 `correct_count = 0`으로 시작해서 정답일 때마다 `correct_count += 1`로 1씩 늘립니다. 마지막에 이 값으로 점수를 계산합니다. 이렇게 값이 계속 바뀌어도 같은 이름으로 다룰 수 있고, 이름만 보고도 무슨 값인지 알 수 있어서 코드가 읽기 쉬워집니다.

**보여줄 코드:** `quiz_game.py`의 `play()` — `correct_count`, `total`, `score`

---

### 1-2. int, str, bool, list, dict의 차이는?

**한 줄 요약:** 정수 / 글자 / 참·거짓 / 순서 있는 목록 / 이름-값 묶음

**🎤 말하기**

> 다섯 가지 모두 퀴즈 한 문제 안에 들어 있습니다.
> 정답 번호 `answer = 3`은 **int**, 정수입니다. 문제 `question`은 **str**, 문자열입니다. 정답인지 확인하는 `is_correct()`는 **bool**, 즉 `True`나 `False`를 돌려줍니다.
> 선택지 4개는 **list**로 저장합니다. 순서가 있어서 `choices[0]`처럼 번호로 꺼냅니다.
> 마지막으로 파일에 저장할 때는 **dict**로 바꿉니다. `{"question": ..., "answer": 3}`처럼 이름표(키)로 값을 찾습니다.
> 정리하면 list는 **순서 번호**로, dict는 **키 이름**으로 값을 꺼낸다는 게 가장 큰 차이입니다.

**보여줄 코드:** `quiz.py`의 `__init__`, `to_dict()`

| 자료형 | 예 |
|---|---|
| int | `answer = 3` |
| str | `question = "고려를 건국한 인물은?"` |
| bool | `quiz.is_correct(1)` → `True` |
| list | `["왕건", "궁예", "견훤", "이성계"]` |
| dict | `{"question": "...", "choices": [...], "answer": 1}` |

### 1-3. if/elif/else로 조건에 따라 다르게 동작하기

**한 줄 요약:** 위에서부터 검사해서 처음 참인 블록 하나만 실행합니다.

**🎤 말하기**

> 메뉴 선택이 대표적인 예입니다. 사용자가 1을 고르면 퀴즈 풀기, 2면 퀴즈 추가, 3이면 목록, 4면 점수 확인, 나머지는 종료입니다.
> `if`에서 첫 조건을 검사하고, 아니면 `elif`로 다음 조건을, 모두 아니면 `else`를 실행합니다. 위에서부터 차례로 보다가 **처음 맞는 하나만** 실행하고 나머지는 건너뜁니다.
> 입력 검증에도 썼습니다. 입력이 비어 있으면 안내하고, 범위를 벗어나면 또 안내하는 식입니다.

**보여줄 코드:** `quiz_game.py`의 `handle_choice()`, `read_number()`

---

### 1-4. for와 while의 차이와 선택 기준

**한 줄 요약:** for는 반복할 대상(횟수)이 정해져 있을 때, while은 조건이 참인 동안 계속할 때

**🎤 말하기**

> 두 반복문을 각각 맞는 곳에 썼습니다.
> 퀴즈 출제는 **for**를 썼습니다. 퀴즈가 7개면 정확히 7번 반복하면 되니까, 목록을 처음부터 끝까지 하나씩 꺼내는 for가 적합합니다.
> 입력 받기는 **while**을 썼습니다. 사용자가 올바른 숫자를 언제 입력할지 미리 알 수 없습니다. 한 번에 맞게 넣을 수도, 다섯 번 틀릴 수도 있습니다. 그래서 `while True`로 계속 묻다가, 올바른 값이 들어오면 `return`으로 빠져나옵니다. 메뉴도 사용자가 종료를 고를 때까지 `while self.running`으로 반복합니다.
> 기준을 정리하면, **몇 번 반복할지 알면 for, 언제 끝날지 모르면 while**입니다.

**보여줄 코드:** `play()`의 `for`, `read_number()`의 `while True`, `run()`의 `while self.running`

### 1-5. 함수 정의, 매개변수, 반환값

**한 줄 요약:** 값을 받아서(매개변수) 일을 하고 결과를 돌려주는(반환값) 재사용 가능한 코드 묶음

**🎤 말하기**

> 가장 많이 재사용한 함수는 `read_number`입니다. 매개변수로 안내 문구, 최솟값, 최댓값 세 개를 받고, 그 범위 안의 올바른 정수를 **반환**합니다.
> 메뉴를 고를 때는 1부터 5, 정답을 고를 때는 1부터 4로 매개변수만 바꿔 같은 함수를 씁니다. 입력 검증 코드를 한 번만 작성하고 여러 곳에서 쓰니까, 검증 규칙을 고칠 때도 이 함수 하나만 고치면 됩니다.
> 다른 예로 `calculate_score(correct_count, total)`은 맞힌 수와 전체 수를 받아 100점 만점 점수를 반환합니다.

**보여줄 코드:** `read_number(self, prompt, min_value, max_value)`, `calculate_score()`

## 2. 클래스와 객체

### 2-1. 클래스란 무엇이고, 왜 사용하나요?

**한 줄 요약:** 데이터(속성)와 동작(메서드)을 하나로 묶은 설계도. 객체는 그 설계도로 만든 실물입니다.

**🎤 말하기**

> 클래스는 붕어빵 틀, 객체는 그 틀로 찍어낸 붕어빵에 비유할 수 있습니다.
> 이 프로젝트에는 클래스가 두 개 있습니다. `Quiz`는 "퀴즈 한 문제"의 설계도이고, 이걸로 퀴즈 객체 7개를 만들었습니다. `QuizGame`은 "게임 전체"의 설계도이고, 객체 하나를 만들어 실행합니다.
> 클래스를 쓰는 이유는 **관련된 데이터와 기능을 한곳에 모으기 위해서**입니다. 문제를 출력하는 기능은 Quiz에, 저장하는 기능은 QuizGame에 있으니 어디를 고쳐야 할지 바로 알 수 있습니다. 실제로 기능이 늘어난 뒤 QuizGame을 별도 파일로 분리하는 리팩터링도 쉽게 할 수 있었습니다.

**보여줄 코드:** `quiz.py`, `quiz_game.py`, `default_quizzes.py`에서 `Quiz(...)`로 객체 생성

---

### 2-2. `__init__` 메서드와 `self`의 역할

**한 줄 요약:** `__init__`은 객체를 만들 때 자동 실행되는 초기화 메서드, `self`는 객체 자기 자신

**🎤 말하기**

> `Quiz("고려를 건국한 인물은?", [...], 1)`처럼 객체를 만들면 `__init__`이 **자동으로 실행**됩니다. 여기서 받은 값으로 문제, 선택지, 정답 속성을 설정합니다. 저는 여기서 선택지가 4개인지, 정답이 1~4인지도 검사해서 잘못된 퀴즈는 아예 만들어지지 않게 했습니다.
> `self`는 **지금 이 객체 자신**을 가리킵니다. 퀴즈 객체가 7개 있어도 `self.question`은 각자 자기 문제를 뜻합니다. 그래서 `quiz.display()`를 호출하면 그 퀴즈의 문제만 출력됩니다.
> 메서드의 첫 번째 매개변수로 항상 `self`를 받고, 호출할 때는 파이썬이 자동으로 넣어 줍니다.

**보여줄 코드:** `quiz.py`의 `__init__`, `quiz_game.py`의 `__init__`

---

### 2-3. 속성(attribute)과 메서드(method)

**한 줄 요약:** 속성은 객체가 가진 값, 메서드는 객체가 하는 일

**🎤 말하기**

> Quiz 객체의 **속성**은 `question`, `choices`, `answer` 세 가지입니다. 객체가 기억하고 있는 데이터입니다.
> **메서드**는 그 데이터를 가지고 하는 동작입니다. `display()`는 자기 문제를 출력하고, `is_correct(번호)`는 정답인지 확인해 True나 False를 돌려줍니다.
> QuizGame도 마찬가지로 `quizzes`, `best_score` 속성을 가지고, `play()`, `add_quiz()`, `save()` 같은 메서드로 게임을 진행합니다.
> 사용할 때는 점(.)으로 접근합니다. `quiz.answer`는 속성, `quiz.display()`처럼 괄호가 붙으면 메서드입니다.

| | 속성 | 메서드 |
|---|---|---|
| Quiz | `question`, `choices`, `answer` | `display()`, `is_correct()`, `correct_choice()`, `to_dict()`, `from_dict()` |
| QuizGame | `quizzes`, `best_score`, `state_file`, `running` | `run()`, `play()`, `add_quiz()`, `list_quizzes()`, `show_score()`, `load()`, `save()` |

## 3. 파일 입출력

### 3-1. 파일을 열고, 읽고, 쓰는 기본 과정

**한 줄 요약:** 열기(`open`) → 읽기/쓰기 → 닫기. `with`를 쓰면 닫기는 자동

**🎤 말하기**

> 파일 작업은 세 단계입니다. 먼저 `open()`으로 파일을 엽니다. 읽을 때는 `"r"`, 쓸 때는 `"w"` 모드를 주고, 한글이 깨지지 않게 `encoding="utf-8"`을 지정합니다.
> 그다음 읽거나 씁니다. 저는 JSON 형식이라 `json.load()`로 읽고 `json.dump()`로 썼습니다.
> 마지막으로 파일을 닫아야 하는데, `with open(...) as file:` 형태로 쓰면 블록이 끝날 때 **자동으로 닫혀서** 닫는 걸 잊을 일이 없습니다.
> 프로그램 시작 시 `load()`로 읽고, 퀴즈를 추가하거나 다 풀었을 때, 종료할 때 `save()`로 씁니다.

**보여줄 코드:** `quiz_game.py`의 `load()`, `save()`

---

### 3-2. JSON이란? 왜 데이터 저장에 쓰나요?

**한 줄 요약:** `{}`와 `[]`로 데이터를 표현하는 텍스트 형식. 파이썬 dict·list와 구조가 같습니다.

**🎤 말하기**

> JSON은 중괄호로 객체를, 대괄호로 배열을 표현하는 텍스트 형식입니다.
> 데이터 저장에 쓴 이유는 세 가지입니다. 첫째, 파이썬의 dict와 list가 JSON의 객체, 배열과 그대로 대응해서 **변환이 쉽습니다**. 둘째, 그냥 텍스트라서 **메모장으로 열어도 읽을 수 있습니다**. 셋째, 거의 모든 프로그래밍 언어가 지원하는 **표준 형식**입니다.
> 다만 Quiz 같은 객체는 JSON에 바로 넣을 수 없어서, `to_dict()`로 dict로 바꿔 저장하고 불러올 때 `from_dict()`로 다시 객체로 만들었습니다.

**보여줄 화면:** 실행 후 생성된 `state.json` 파일

### 3-3. try/except로 오류 처리하기

**한 줄 요약:** 오류가 날 수 있는 코드를 try에 넣고, 오류가 나면 except에서 처리해 프로그램이 멈추지 않게 합니다.

**🎤 말하기**

> 사용자가 숫자 대신 abc를 입력하면 `int("abc")`에서 `ValueError`가 발생합니다. 그냥 두면 프로그램이 빨간 에러를 내고 종료됩니다.
> 그래서 `try`로 감싸고 `except ValueError`에서 "숫자를 입력해 주세요"라고 안내한 뒤 다시 입력받게 했습니다.
> 파일도 마찬가지입니다. state.json이 깨져 있으면 JSON을 읽다가 오류가 나는데, 이걸 잡아서 기본 퀴즈 데이터로 복구합니다. Ctrl+C를 누르면 생기는 `KeyboardInterrupt`도 잡아서 데이터를 저장한 뒤 안전하게 종료합니다.
> 실제로 파일을 일부러 망가뜨리고 Ctrl+C도 눌러서 테스트했고, 그 결과를 README에 넣었습니다.

**보여줄 코드:** `read_number()`의 `try/except ValueError`, `load()`의 `except`, `run()`의 `except (KeyboardInterrupt, EOFError)`

## 4. Git 기초

### 4-1. Git이란? 왜 필요한가요?

**한 줄 요약:** 파일의 변경 이력을 기록하는 버전 관리 도구

**🎤 말하기**

> Git은 파일이 언제, 어떻게, 왜 바뀌었는지 기록하는 버전 관리 도구입니다. 게임의 세이브 포인트와 비슷합니다.
> 필요한 이유는 네 가지입니다. 첫째, 변경 **기록**이 남습니다. 이 프로젝트의 커밋 로그를 보면 메뉴, Quiz 클래스, 퀴즈 풀기 순서로 개발한 과정이 그대로 보입니다. 둘째, 잘못 고쳤을 때 이전 상태로 **되돌릴** 수 있습니다. 셋째, **브랜치**로 기존 코드를 건드리지 않고 새 기능을 만들 수 있습니다. 넷째, GitHub에 올려 **백업**하고 다른 사람과 **협업**할 수 있습니다.

**보여줄 화면:** `git log --oneline --graph`

---

### 4-2. init, add, commit, push, pull, checkout, clone

**한 줄 요약:** 저장소 만들기 → 고르기 → 기록 → 올리기 / 받기 / 브랜치 이동 / 복제

**🎤 말하기**

> 작업 순서대로 설명하겠습니다.
> `init`은 폴더를 Git 저장소로 만듭니다. 그다음 파일을 고치면 `add`로 이번에 기록할 변경을 고르고, `commit`으로 메시지와 함께 이력에 확정합니다. 저는 기능 하나를 완성할 때마다 add와 commit을 했습니다.
> `push`는 내 컴퓨터의 커밋을 GitHub에 올리고, 반대로 `pull`은 GitHub에 새로 올라온 커밋을 내 컴퓨터로 받아옵니다.
> `checkout`은 브랜치를 옮겨 다니는 명령이고, `-b`를 붙이면 새 브랜치를 만들면서 이동합니다.
> 마지막으로 `clone`은 GitHub 저장소 전체를 내 컴퓨터에 처음 복사해 오는 명령입니다.

| 명령 | 한 줄 설명 | 비유 |
|---|---|---|
| `init` | 폴더를 Git 저장소로 만듦 | 일기장 새로 펴기 |
| `add` | 기록할 변경 고르기 (스테이징) | 사진 고르기 |
| `commit` | 고른 변경을 이력으로 확정 | 앨범에 붙이고 날짜 적기 |
| `push` | 내 커밋을 원격에 올림 | 클라우드에 업로드 |
| `pull` | 원격의 새 커밋을 받아 합침 | 클라우드에서 동기화 |
| `checkout` | 브랜치 이동 (`-b`: 생성+이동) | 다른 작업 공간으로 이동 |
| `clone` | 원격 저장소 전체를 처음 복제 | 앨범 통째로 복사해 오기 |

---

### 4-3. 브랜치 생성과 병합

**한 줄 요약:** 새 브랜치에서 따로 개발하고, 완성되면 main에 합칩니다.

**🎤 말하기**

> 퀴즈 풀기 기능을 브랜치로 개발했습니다.
> `git checkout -b feature/play-quiz`로 새 브랜치를 만들고 이동했습니다. 이 브랜치에서 퀴즈 풀기 기능을 만들고 커밋했습니다. 이 동안 main 브랜치의 코드는 그대로라서, 개발 중에 문제가 생겨도 main은 안전합니다.
> 기능이 완성되자 `git checkout main`으로 돌아와서 `git merge --no-ff feature/play-quiz`로 병합했습니다. `--no-ff` 옵션을 줘서 그래프에 갈라졌다가 합쳐진 기록이 남게 했습니다.

```
*   Merge branch 'feature/play-quiz' into main
|\
| * feat: 퀴즈 풀기 기능 구현
|/
* feat: 한국사 기본 퀴즈 데이터 7개 작성
```

### 4-4. 원격 저장소를 clone하고, pull로 변경사항 가져오기

**한 줄 요약:** clone은 처음 한 번 전체 복제, pull은 이미 있는 저장소에 새 변경만 가져오기

**🎤 말하기**

> 두 명이 협업하는 상황을 혼자 재현해 봤습니다.
> 먼저 GitHub 저장소를 `git clone`으로 `TEST-EI-1-clone`이라는 다른 폴더에 복제했습니다. 이 폴더를 다른 사람의 컴퓨터라고 생각하면 됩니다. 여기서 README에 한 줄을 추가하고 commit, push했습니다.
> 그다음 원래 작업 폴더로 돌아오면, 이 폴더에는 아직 그 변경이 없습니다. 여기서 `git pull origin main`을 실행하니 방금 올린 README 변경이 내려와서 반영된 것을 확인했습니다.
> 차이를 정리하면, clone은 저장소가 **없을 때** 처음 한 번, pull은 저장소가 **이미 있을 때** 새 변경만 가져오는 것입니다.

```
[다른 폴더]  git clone → README 수정 → git commit → git push
                                                       ↓
                                                    GitHub
                                                       ↓
[원래 폴더]                                         git pull  → README 반영 확인
```

## 예상 꼬리 질문

| 질문 | 짧은 답 |
|---|---|
| `=`와 `==`의 차이는? | `=`는 변수에 값 저장, `==`는 두 값이 같은지 비교 |
| list와 dict 중 퀴즈 목록은 왜 list? | 퀴즈는 순서대로 출제하고 번호로 보여주니까 순서가 있는 list가 맞음 |
| `while True`는 무한 반복 아닌가요? | 올바른 입력이면 `return`으로 빠져나오므로 무한히 돌지 않음 |
| `return`이 없는 함수는? | `None`을 반환. 예: `show_score()`는 출력만 하고 값은 돌려주지 않음 |
| `self`를 안 쓰면? | 객체의 속성에 접근할 수 없음. `question`만 쓰면 지역 변수로 취급됨 |
| `with` 없이 열면? | 직접 `file.close()`를 해야 하고, 중간에 오류가 나면 닫히지 않을 수 있음 |
| `except:`만 쓰면 안 되나요? | 모든 오류를 숨겨 버그를 찾기 어려움. 예상한 오류만 골라 잡는 것이 좋음 |
| commit과 push의 차이는? | commit은 내 컴퓨터에 기록, push는 그 기록을 GitHub에 올림 |
| merge 충돌이 나면? | 같은 줄을 양쪽에서 고친 경우. 파일을 열어 어느 쪽을 남길지 정하고 다시 커밋 |
| 랜덤 출제는 어떻게? | `random.shuffle()`로 퀴즈 목록 복사본을 섞어 출제 (보너스 과제) |
